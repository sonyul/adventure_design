> **이 문서를 읽는 법**
> - 이 문서는 "뉴스 봐"에서 **무엇을 지켜야 하고, 누가 어떻게 공격할 수 있으며, 그것을 어떻게 막는지**, 그리고 **개인정보를 어떻게 다루는지**를 정한 문서입니다.
> - 과제 규모(사용자 1명, 회원 기능 없음, 비용 0원)에 맞게 **꼭 필요한 대비책만** 적었습니다. 은행 앱 수준의 보안을 목표로 하지 않습니다.
> - **✅ 확정** = 앞 문서(02·03·04·06·08)에서 ✅로 이미 정해진 내용입니다. 근거를 함께 적었습니다.
> - **✅ 추천대로 확정** = 이 문서에서 처음 정한 기술 세부 중 **나중에 쉽게 고칠 수 있는 것**입니다. 사용자 기준 "나중에 쉽게 고칠 수 있는 기술 세부는 추천대로 정한다"에 따라 확정으로 둡니다.
> - 사용자 판단이 필요했던 3건은 [10장](#10-사용자-확인이-필요한-항목)에 기록했고, v1.1에서 모두 답을 받았습니다.
> - **🔍 확인 못 함** = 이번에 공식 문서로 확인하지 못한 것입니다. 구현·시험 때 확인합니다.
> - 상태 기호: ✅ 완료(확정) · ⚠ 부분 · 🔴 미작성 · ⏳ 진행
>
> **약어·용어 풀이**
> - **FR**(Functional Requirement, 기능 요구) · **NFR**(Non-Functional Requirement, 비기능 요구): [기능명세서](03_기능명세서.md)의 번호를 그대로 씁니다.
> - **ADR**(Architecture Decision Record, 설계 결정 기록): [아키텍처·ADR](08_아키텍처_ADR.md)의 번호를 그대로 씁니다.
> - **위협 모델**: "무엇을 지킬지(자산) → 누가 어떻게 해칠 수 있는지(위협) → 어떻게 막을지(대비책)"를 정리한 표
> - **자산**: 지켜야 할 대상. 예) 비밀 열쇠, 데이터, 서비스가 계속 돌아가는 것
> - **인증**(로그인): "너는 누구냐"를 확인하는 것 · **권한**(인가): "너는 무엇을 해도 되냐"를 정하는 것
> - **익명 로그인**: Firebase가 이름·이메일 없이 앱 설치마다 **무작위 사용자 번호(UID)** 를 하나 만들어 주는 로그인 방식
> - **UID**(User ID, 사용자 번호): Firebase 로그인이 사용자마다 붙이는 고유 번호(무작위 글자). 비밀번호가 아니므로 알아도 그 사람으로 로그인할 수는 없습니다.
> - **보안 규칙**(Firestore Security Rules): Firestore가 앱의 읽기·쓰기 요청마다 "허락할지"를 검사하는 규칙 글. Firebase 콘솔에 올려 둡니다.
> - **서비스 계정**: 사람이 아니라 프로그램(파이썬 스크립트)이 Firebase에 접속할 때 쓰는 전용 계정. 그 **열쇠 파일**(JSON 형식)을 가진 쪽은 관리자처럼 접근할 수 있습니다.
> - **GitHub Secrets**(비밀 저장소): GitHub에 비밀번호·키를 코드와 따로 숨겨 두는 칸. 실행할 때만 스크립트에 전달됩니다.
> - **API 키**(API Key): 외부 서비스(네이버·Gemini)를 부를 때 "나는 허락받은 사용자"임을 보여주는 비밀 글자열
> - **포크**(fork): 남의 공개 저장소를 자기 계정으로 복사하는 것 · **PR**(Pull Request): 남이 "내 수정을 넣어 달라"고 보내는 요청
> - **공급망 공격**: 내가 가져다 쓰는 외부 부품(라이브러리)이 바뀌거나 오염되어 내 프로그램이 해를 입는 것
> - **프롬프트 주입**(Prompt Injection): AI에 넣는 글(여기서는 뉴스 본문) 속에 "앞 지시를 무시하고 ○○해라" 같은 문장을 숨겨 AI를 엉뚱하게 움직이려는 공격
> - **Spark 요금제**: Firebase의 무료 요금제(카드 등록 없음). 한도를 넘으면 요금이 붙는 대신 **그날 사용이 멈춥니다**.
> - **SHA**(Secure Hash Algorithm, 고유 지문): 여기서는 GitHub 부품의 특정 버전을 가리키는 40자리 지문 글자열
> - **PIPA**(개인정보 보호법): 대한민국 개인정보 보호법

| # | 원칙 | 뜻 | 상태 |

| W13 | 휴대폰 분실 | AS8 | 하 | 하 | **하** | 민감 정보가 없으므로 별도 암호화 안 함. 휴대폰 화면 잠금만 권장 | ✅ 추천대로 |

### 2-4. "공개 저장소 + 회원 없음" 조합에서 꼭 기억할 3가지

1. **앱 설정 정보는 공개된 것과 같다** — 저장소에 안 올려도 설치 파일을 풀면 나옵니다. 그래서 숨기기에 기대지 않고 **보안 규칙이 유일한 문**입니다(3장).
2. **익명 로그인은 아무나 할 수 있다** — "로그인했으면 허락"(`request.auth != null`)만으로는 **남도 통과**합니다. 그래서 **주인의 UID만** 허락하는 규칙을 추천합니다(3-3, ✅ Q1-A 확정).
3. **비밀은 실행 순간에만 존재해야 한다** — Secrets → 환경 변수 → 메모리. 파일·로그·실행 기록(D2)에는 남기지 않습니다(4장).

  1. 앱이 시작할 때 이미 로그인되어 있는지 확인하고, 아니면 `signInAnonymously()`로 익명 로그인합니다(공식 안드로이드 방법, 콘솔에서 "익명" 로그인 제공자를 켜야 함 — 공식 문서 확인).

  3. 로그인 실패·권한 거부는 화면에 새 문구를 만들지 않고 **기존 안내 문구**(S01 저장 실패 M2, S02 불러오기 실패 M4, S04 M10)로 보여줍니다 → 04 변경 없음.

### 3-3. 허락 대상 — "주인 UID 고정" (✅ Q1-A 사용자 확정)

| 기준 | **A. 주인 UID 1개만 허락** (추천) | B. 익명 로그인한 누구나 허락 + 값 검사 |
|---|---|---|
| 남이 `settings/me` 바꾸기 (W3) | 막힘 | **막지 못함** (값 검사로 이상한 값만 막음, 정상 분야로 바꾸는 것은 가능) |
| 남이 읽기 반복 (W5) | 막힘 | 막지 못함 (요금은 0원이지만 그날 앱이 멈출 수 있음) |
| 남이 `editions` 읽기 | 막힘 | 가능 (공개 뉴스 요약이라 피해는 작음) |
| 처음 설정 | 앱을 한 번 실행 → 콘솔 Authentication 사용자 목록에서 UID 복사 → 규칙에 붙여넣기 (5분) | 없음 |
| **앱을 다시 깔거나 데이터를 지우면** | UID가 바뀜 → 앱이 "불러오지 못했어요"만 보임 → **콘솔에서 규칙의 UID를 새 값으로 바꿔야 함** (5분) | 그대로 동작 |
| 휴대폰 교체 | 위와 같음 | 그대로 동작 |

- **추천: A** — 공개 저장소에서 남이 내 분야 설정을 바꾸거나 한도를 소진하는 것을 확실히 막습니다. 대가는 "재설치 때 콘솔에서 UID 한 줄 바꾸기"입니다.
- 사용자 판단이 필요한 이유: 시연 직전에 휴대폰을 초기화하거나 앱을 다시 깔면 **UID를 바꾸는 운영 단계**가 생깁니다. 이 수고를 받아들일지 결정이 필요합니다.
- 규칙은 콘솔에서 언제든 바꿀 수 있으므로 A ↔ B 전환은 쉽습니다.
- UID는 비밀번호가 아니므로(알아도 그 사람으로 로그인 못 함) 규칙 파일을 저장소에 올려도 됩니다. 다만 저장소에는 **자리표시 글자**(`OWNER_UID_HERE`)로 두고 실제 값은 콘솔에만 넣는 것을 추천합니다(✅ 추천대로 — 재설치 때 저장소를 고칠 필요가 없음).

### 3-4. 보안 규칙 초안 (규칙 파일은 만들지 않고 문서 안에만 둠)

> - **문법 확인 범위 (2026-10-26, 공식 문서)**: `rules_version = '2';`, `service cloud.firestore`, `match /databases/{database}/documents`, `allow get / list / create / update / delete`, `function` 정의, `request.auth != null`, `request.auth.uid`, `request.resource.data`, `keys().hasAll([...])`, `keys().hasOnly([...])`, `is string`, "허락하는 규칙이 없으면 거부" — **확인함**.
> - **🔍 확인 못 함**: 목록 포함 검사 `값 in [목록]`, 글자 패턴 검사 `.matches('정규식')`, 서버 시각 비교 `== request.time`(앱이 "서버 시각"으로 저장할 때 같아지는지) — 공식 참조 페이지를 이번에 끝까지 읽지 못했습니다. 널리 쓰이는 문법이지만 **Firebase 콘솔의 "규칙 놀이터"(Rules Playground)나 에뮬레이터로 시험한 뒤** 올립니다([10](10_테스트_QA.md)).
> - 깊은 분야 47개 목록을 규칙에 전부 넣지 않고 "큰 분야 코드 + `_` + 영어 소문자" 모양만 검사합니다. 정확한 소속 검사는 스크립트가 다시 합니다(06 R9, `SETTINGS_INVALID`) → 이중 검사.

```
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {

    // ── 주인 확인 (Q1-A 확정). B안이면 return request.auth != null; 로 바꿈
    function isOwner() {
      return request.auth != null
          && request.auth.uid == 'OWNER_UID_HERE';   // 콘솔에서 실제 UID로 교체
    }

    // ── 큰 분야 코드 10개 (06 4-8)
    function bigCategories() {
      return ['politics','economy','society','world','it',
              'science','nature','culture','sports','life'];
    }

    // ── settings/me 값 검사 (06 3-1, R9)
    function validSettings(d) {
      return d.keys().hasOnly(['firstCategory','deepCategory','secondCategory',
                               'updatedAt','schemaVersion'])
          && d.keys().hasAll(['firstCategory','deepCategory','secondCategory',
                              'updatedAt','schemaVersion'])
          && d.firstCategory is string
          && d.secondCategory is string
          && d.deepCategory is string
          && d.firstCategory in bigCategories()              // 🔍 in 문법 시험 필요
          && d.secondCategory in bigCategories()
          && d.firstCategory != d.secondCategory
          && d.deepCategory.matches(d.firstCategory + '_[a-z]+')   // 🔍 matches 시험 필요
          && d.updatedAt == request.time                     // 🔍 서버 시각 저장 시 시험 필요
          && d.schemaVersion == 1;
    }

    // ── D1 사용자 설정: 문서 1개만, 주인만 읽기·쓰기, 지우기 금지
    match /settings/me {
      allow get: if isOwner();
      allow create, update: if isOwner() && validSettings(request.resource.data);
      allow delete: if false;
    }

    // ── 회차 결과: 주인만 읽기(최신 1개 조회 = list, 문서 ID로 읽기 = get), 쓰기 전부 금지
    match /editions/{editionId} {
      allow get, list: if isOwner();
      allow create, update, delete: if false;
    }

    // ── runs(실행 기록), 그 밖의 모든 경로: 규칙 없음 → 앱은 전부 거부 (스크립트·콘솔만)
  }
}
```

| 경로 | 앱 읽기 | 앱 쓰기 | 스크립트 (서비스 계정) | 근거 | 상태 |
|---|:---:|:---:|:---:|---|:---:|
| `settings/me` | 주인만 | 주인만 + 값 검사, 삭제 금지 | 읽기 | 06 8-1 ✅ | ✅ 추천대로 / 주인 범위 ✅ Q1-A |
| `settings/` 의 다른 문서 | × | × | — | 사용자 1명 | ✅ 추천대로 |
| `editions/*` | 주인만 (`get`·`list`) | × | 쓰기·읽기 | 06 8-1 ✅ | ✅ 추천대로 |
| `runs/*` | × | × | 쓰기 | 06 8-1 "앱은 필요 없음" → **앱 접근 없음으로 확정** (03 9장 "앱·사람이 읽음" 정리, [11장](#11-앞-문서와-어긋나는-점-보고만)) | ✅ 추천대로 |
| 그 밖 | × | × | — | 기본 거부 | ✅ |

- 처음 Firestore를 만들 때 고르는 "테스트 모드"(일정 기간 누구나 허락) 규칙은 **쓰지 않고**, 처음부터 위 규칙(또는 "모두 거부")으로 시작합니다 (✅ 추천대로).

### 4-2. 서비스 계정 범위 줄이기 (C12, ✅ 추천대로)

- Firebase가 자동으로 만들어 주는 관리자용 서비스 계정 대신, **스크립트 전용 서비스 계정**을 새로 만들고 **Firestore 읽기·쓰기 역할만**(구글 클라우드 역할 이름 "Cloud Datastore User", 🔍 구현 때 콘솔에서 이름 확인) 줍니다. 유출되어도 인증·다른 서비스는 건드리지 못합니다.
- 어렵거나 동작하지 않으면 자동 서비스 계정으로 시작해도 됩니다(콘솔에서 언제든 바꿀 수 있음). 이 경우 W9 위험이 커진다는 점만 기록합니다.
- 열쇠 파일은 내려받은 뒤 Secrets에 붙여넣고 **PC에서 바로 지웁니다**(다운로드 폴더에 남겨 두지 않기).

### 4-3. 앱 설정 파일(`google-services.json`)을 공개해도 되나

| 사실 (Firebase 공식 문서 확인) | 우리에게 뜻하는 것 |
|---|---|
| Firebase용 API 키는 프로젝트를 **"식별"** 할 뿐, 일반적인 비밀이 아니며 코드·설정 파일에 넣어도 된다 | 이 파일이 공개되어도 그것만으로 데이터가 털리지는 않음. 데이터는 **보안 규칙**이 지킴 |
| 키를 숨기는 것에만 기대지 말 것 | → 원칙 P2 |
| **Gemini API 키는 코드·설정 파일에 절대 넣지 말 것**, 공개용 키의 허용 목록에 Gemini API를 넣지 말 것 | Gemini 키는 Secrets에만. Firebase 앱 키의 허용 API 목록에 Gemini API가 들어가지 않았는지 콘솔에서 확인 (C16) |

- 결정 (✅ 추천대로): 공개해도 되지만 **저장소에는 올리지 않습니다**(`.gitignore`). 이유: 자동 비밀 검사 도구가 구글 키 모양을 보고 경고를 띄워 혼란스럽고, 올리지 않아도 손해가 없습니다. 단, **설계는 "이미 공개됨"을 가정**합니다(설치 파일을 풀면 나오므로).
- Gemini 키를 만들 때 Firebase 프로젝트와 **같은 구글 클라우드 프로젝트**에 만들게 될 수 있습니다. 이때 앱 키에 Gemini가 허용되지 않도록 C16을 지킵니다(🔍 AI Studio 화면에서 프로젝트 선택 방식은 구현 때 확인).

### 4-5. 실행 로그·실행 기록에 비밀을 남기지 않는 규칙 (C5, ✅ 추천대로)

> 공개 저장소의 GitHub Actions 실행 로그는 **누구나 볼 수 있는 것으로 보고** 설계합니다(🔍 공식 문서로 확인 못 함 — 공개로 가정하는 쪽이 안전).
> 공식 문서 확인: ① Secrets 값은 로그에서 자동으로 가려지지만 **"가려짐이 보장되지는 않는다"**. ② 비밀을 **JSON 같은 구조 데이터로 묶으면 가려지기 어렵다**. ③ 비밀에서 만들어 낸 값(예: 인코딩한 값)은 따로 비밀로 등록하거나 `::add-mask::`로 가려야 한다. ④ 비밀을 명령줄 인자로 넘기지 말고 환경 변수로 넘길 것.

| # | 규칙 | 근거 |
|:---:|---|---|
| L1 | 비밀은 워크플로에서 **환경 변수(`env:`)로만** 스크립트에 넘김. 명령줄 인자·파일 쓰기 금지 | 공식 ④ |
| L2 | 스크립트는 열쇠 JSON을 환경 변수에서 읽어 **메모리에서 바로** Firebase 부품에 넘김. 디스크에 파일로 쓰지 않음 | 공식 ② — 서비스 계정 JSON은 구조 데이터라 자동 가림이 잘 안 될 수 있음 |
| L3 | `print`/로그로 **환경 변수·설정값 전체·요청 헤더·요청 주소 전체를 출력하지 않음**. 네이버 요청 헤더(Client Secret 포함), Gemini 요청(키 포함)을 로그에 남기지 않음 | 공식 ① |
| L4 | 외부 부품의 디버그 출력(요청 내용 전부 찍기)을 켜지 않음. 워크플로에 `set -x`(명령 그대로 출력) 쓰지 않음 | 공식 ① |
| L5 | 예외(오류) 메시지를 그대로 로그·D2 `errorMessage`에 넣기 전에 **짧은 설명으로 바꿔 씀** (예: "네이버 API 401 오류"). 오류 객체 통째 출력 금지 — 일부 부품은 오류 안에 요청 주소·헤더를 담음 | 06 12-1 ⑥ |
| L6 | D2 `errorMessage`·`warnings[].detail`에는 **오류 종류·숫자·페이지 이름만** 넣음. 키, 서비스 계정 이메일·프로젝트 내부 정보, 질의 문자열이 붙은 주소는 넣지 않음 | 06 3-2·12-1 ⑥ |
| L7 | 비밀에서 만든 값(예: 인코딩·일부 잘라낸 값)이 생기면 `::add-mask::`로 가림. 원칙적으로 만들지 않음 | 공식 ③ |
| L8 | 실수로 로그에 찍혔다면: **로그 삭제 + 그 비밀을 즉시 폐기·재발급**(4-7). 로그를 지워도 이미 복사됐을 수 있으므로 재발급이 핵심 | 아래 4-7 |

- 로그 형식·보존 기간 자체는 [관측·로깅·감사(12)](12_관측_로깅_감사.md)에서 정합니다. 이 표는 **비밀을 남기지 않는 규칙**만 정합니다.

| 공개 뉴스 기사 **제목·요약·추출한 본문 일부(기사당 3,000자까지)**, 언론사·날짜, 지시문·예시 제목 | 사용자 분야 선택(`settings/me`), 익명 UID, 실행 기록, 키·비밀, 그 밖의 어떤 사용자 정보 |

- 무료 요금제는 **보낸 내용이 구글 제품 개선에 쓰입니다**(02 5-4 ✅) → 공개 뉴스만 보내므로 문제 없음(NFR-07 ✅).
- 분야 키워드(예: "우주, NASA")는 네이버 검색어로만 쓰고 AI에는 보내지 않습니다. 🔍 단, 추천 뉴스 묶기 지시문에 분야 이름을 넣는다면 그것은 "관심 분야"라는 약한 취향 정보입니다 — 이름만으로 사람을 알 수 없고 사용자 본인 1명이므로 허용합니다 (✅ 추천대로, 구현 시 지시문에 넣지 않아도 되면 넣지 않음).
- Gemini 키를 만든 구글 클라우드 프로젝트에 **결제 수단을 등록하지 않습니다** (P6) — 결제를 켜면 요금이 붙을 수 있습니다.

### 5-5. 접근 통제

## 10. 사용자 확인이 필요한 항목

> 되돌리기 어렵거나 사용자 판단이 필요한 것만 중요한 순서로 적었습니다. 나머지 기술 세부는 "✅ 추천대로 확정"했습니다.

| 우선 | 질문 | 추천안 | 왜 사용자 판단이 필요한가 | 관련 |
|:---:|---|---|---|---|
| ✅ Q1 (사용자 확정 v1.1: **A**) | 앱의 Firestore 접근을 **"주인 UID 1개만 허락"**(A)으로 할까요, **"익명 로그인한 누구나 + 값 검사"**(B)로 할까요? | **A** — 공개 저장소라 남이 같은 프로젝트에 접속할 수 있으므로, 분야 설정 변경·한도 소진을 확실히 막음 | A는 앱을 다시 깔거나 휴대폰을 바꾸면 **콘솔에서 규칙의 UID를 바꾸는 운영 단계(5분)** 가 생깁니다. 시연 직전에 이 일이 생길 수 있음 | 3-3, W3·W5 |
| ✅ Q2 (사용자 확정 v1.1: **그렇게**) | 과제(제출·평가)가 끝나면 **예약 실행을 끄고 키 3종을 폐기**할까요? (데이터는 06 결정대로 계속 보관) | **그렇게** — 쓰지 않는 키가 살아 있으면 유출 위험만 남음. 저장소가 공개라 60일 정도 변화가 없으면 예약 실행이 자동으로 꺼지는 것으로 알려져 있음(08 ADR-010 메모) | 키를 폐기하면 다시 쓰려면 재발급·재설정이 필요 | 5-3 |
| ✅ Q3 (사용자가 직접 켬 — 늦어도 GitHub 저장소를 만들고 Secrets에 키를 넣기 전까지) | GitHub·구글 계정에 **2단계 인증**이 켜져 있나요? (안 켜져 있다면 켜 주세요) | 켜기 | 본인 계정 설정이라 사용자만 할 수 있음 | C13, W10 |

**추천대로 확정한 기술 세부 (나중에 쉽게 고칠 수 있음)**: 익명 로그인 방식, 보안 규칙 초안(값 검사 포함), `runs` 앱 접근 없음, Secrets 이름, 전용 서비스 계정, `google-services.json` 미커밋, `.gitignore`, 로그 규칙, 워크플로 권한, 버전·SHA 고정, AI 결과 검사·링크 제한, 분석·오류보고 부품 미사용, 백업 끄기, 앱 권한 목록, 저작권 세부 규칙.

## 참고 자료 (2026-10-26 확인)

- 보안 규칙 조건·`request.auth`·`request.resource.data`, 서버용 부품은 보안 규칙을 모두 건너뜀: [firebase.google.com — Writing conditions for Cloud Firestore Security Rules](https://firebase.google.com/docs/firestore/security/rules-conditions)
- `rules_version = '2'`, `get`·`list`·`create`·`update`·`delete`, `function`, 기본 거부: [firebase.google.com — Security Rules language](https://firebase.google.com/docs/rules/rules-language)
- `keys().hasAll`·`keys().hasOnly`·`is string`: [firebase.google.com — Control access to specific fields](https://firebase.google.com/docs/firestore/security/rules-fields)
- Firebase API 키는 비밀이 아님·Gemini 키는 코드에 넣지 말 것: [firebase.google.com — Learn about using and managing API keys for Firebase](https://firebase.google.com/docs/projects/api-keys)
- 안드로이드 익명 로그인(`signInAnonymously`, 콘솔에서 켜기, 자동 정리는 업그레이드 필요): [firebase.google.com — Authenticate with Firebase Anonymously on Android](https://firebase.google.com/docs/auth/android/anonymous-auth)
- 포크 실행에는 Secrets 미전달, `::add-mask::`: [docs.github.com — Using secrets in GitHub Actions](https://docs.github.com/en/actions/security-for-github-actions/security-guides/using-secrets-in-github-actions)
- 자동 가림 보장 안 됨·구조 데이터 주의·`pull_request_target` 위험·SHA 고정: [docs.github.com — Secure use reference](https://docs.github.com/en/actions/reference/security/secure-use)
- **확인하지 못한 것**: 규칙 문법 `in`·`matches`·`request.time` 비교, 익명 로그인 재설치 시 UID 변경, 공개 저장소 Actions 로그 공개 범위·보존 기간, 비밀 검사 무료 여부, 수동 실행 권한, 서비스 계정 역할 이름, Firestore 저장 시 자동 암호화, 익명 로그인 처리 위치, 시간 변경 신호 권한, 부팅 신호 부품 exported 값, 백업 시 로그인 상태 복원 동작.
