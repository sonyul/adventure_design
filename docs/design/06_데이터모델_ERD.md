> **약어·용어 풀이**
> - **ERD**(Entity-Relationship Diagram, 개체-관계도): 저장하는 데이터 덩어리(개체)와 그 사이의 연결(관계)을 그린 그림
> - **FR**(Functional Requirement, 기능 요구) · **NFR**(Non-Functional Requirement, 비기능 요구): [기능명세서](03_기능명세서.md)의 번호를 그대로 씁니다.
> - **Firestore**(파이어스토어): 구글 Firebase의 **문서형 데이터베이스**. 엑셀처럼 칸이 고정된 표가 아니라, "이름: 값" 묶음(문서)을 폴더(컬렉션)에 넣어 두는 방식입니다.
> - **컬렉션**(collection): 문서들을 담는 폴더. 예) `editions`
> - **문서**(document): 컬렉션 안의 데이터 한 건. 고유한 이름(문서 ID)이 있습니다. 예) `editions/20261026-1130`
> - **필드**(field): 문서 안의 "이름: 값" 한 쌍. 예) `slot: "noon"`
> - **맵**(map): 필드 안에 다시 "이름: 값" 묶음을 넣은 것 (작은 문서처럼 생김)
> - **배열**(array): 값 여러 개를 순서대로 담은 목록
> - **타임스탬프**(timestamp): 날짜+시각 값. Firestore는 세계 표준시(UTC)로 저장하고, 앱·스크립트가 한국 시각(KST, Korea Standard Time)으로 바꿔 보여줍니다.
> - **인덱스**(index): 책 뒤의 "찾아보기"처럼, 데이터를 빨리 찾으려고 데이터베이스가 따로 만들어 두는 목록. Firestore는 필드마다 자동으로 만듭니다.
> - **캐시**(cache, 휴대폰 안 보관): 인터넷에서 한 번 읽은 데이터를 휴대폰에 복사해 두는 것
> - **SharedPreferences**(셰어드 프리퍼런스): 안드로이드 앱이 "이름: 값" 몇 개를 휴대폰 안에 간단히 저장하는 기본 기능
> - **KST**(Korea Standard Time, 한국 표준시) · **UTC**(Coordinated Universal Time, 세계 표준시)
> - **MiB/GiB**: 저장 용량 단위. 1 MiB ≈ 105만 바이트, 1 GiB ≈ 10억 7천만 바이트. 한글 1글자는 보통 3바이트입니다.
> - **회차**: 하루 3번(6:30·11:30·18:30 KST) 스크립트가 한 번 실행되어 만든 결과 한 묶음

## 2. ERD (문서형 데이터베이스에 맞춘 관계 그림)

### 2-1. 전체 그림 ✅

> Firestore는 표끼리 "연결 열쇠"로 묶는 방식(관계형 DB)이 아니라 **문서 안에 내용을 포개 넣는 방식**입니다. 그래서 아래 그림의 `[ ]` 상자는 컬렉션/문서, 들여쓴 `└` 줄은 **같은 문서 안에 포개진 내용**, 점선 화살표는 **문서 ID를 적어 가리키는 관계**입니다.

```
 Firestore (데이터베이스 1개)
 │
 ├─ [settings] 컬렉션
 │     └─ [me] 문서 ............ D1 사용자 설정 (딱 1개, 앱이 씀 / 스크립트가 읽음)
 │            firstCategory · deepCategory · secondCategory · updatedAt
 │
 ├─ [runs] 컬렉션 .............. D2 실행 기록 (회차마다 1개, 스크립트만 씀)
 │     └─ [20261026-1130] 문서
 │            slot · status · startedAt · ... · warnings[ ]
 │            editionId ─ ─ ─ ─ ─ ─ ─ ─ ┐  (결과를 저장했으면 같은 ID, 아니면 비어 있음)
 │                                      ▼
 └─ [editions] 컬렉션 .......... 회차 결과 (회차마다 1개, 스크립트가 씀 / 앱이 읽음)
       └─ [20261026-1130] 문서
              slot · createdAt · notifyArticleId ─ ─ ┐ (알림용 한 줄이 있는 기사 번호)
              │                                      │
              ├─ articles[ ] ........ D3 종합 기사 (페이지마다 0~3개, 최대 9개)
              │     └─ { articleId ◀─ ─ ─ ─ ─ ─ ─ ─ ┘
              │          page · order · hookLine · title · body · conclusion · isNotify
              │          ├─ words[ ] ..... D4 어려운 단어 해설 (0~5개)
              │          │     └─ { word · explanation }
              │          └─ sources[ ] ... D5 출처 (1~5개)
              │                └─ { press · title · url · linkType · publishedAt · extractResult }
              │        }
              └─ otherLines[ ] ...... D7 다른 분야 한 줄 (0~8개)
                    └─ { category · hookLine · articleTitle · url · linkType · press · publishedAt }

 휴대폰 안 (K7)
 ├─ Firestore 자동 보관(캐시) ...... 위 settings/me, 최근 읽은 editions 문서의 복사본
 └─ SharedPreferences
        lastNotifiedArticleId ─ ─ ─ ▶ editions/…/articles[].articleId  (중복 알림 막기)
        lastNotifiedAt
```

### 2-2. 관계 요약 ✅

| 관계 | 개수 | 어떻게 연결하나 | 근거 |
|---|:---:|---|---|
| D1 사용자 설정 → 실행 | 1 : 여러 회차 | 스크립트가 실행마다 `settings/me`를 읽고, 그때 쓴 분야를 실행 기록 `categoriesUsed`에 복사해 남김 | FR-01-2 ✅ |
| D2 실행 기록 → 회차 결과 | 1 : 0 또는 1 | **문서 ID를 똑같이** 씀 (`runs/20261026-1130` ↔ `editions/20261026-1130`). 새로 만든 기사가 하나도 없으면 회차 결과는 저장하지 않음(`editionId` 비움) | FR-02-6 예외 ✅ |
| 회차 결과 → D3 종합 기사 | 1 : 0~9 | 같은 문서 안 `articles` 배열 | 03 9장 ✅, 위치 ✅ 추천대로 |
| D3 → D4 단어 해설 | 1 : 0~5 | 기사 안 `words` 배열 | 03 9장 ✅ (D3 안에 포함) |
| D3 → D5 출처 | 1 : 1~5 | 기사 안 `sources` 배열 | 03 9장 ✅, FR-02-5 (출처 0개 기사 안 만듦) |
| 회차 결과 → D7 다른 분야 한 줄 | 1 : 0~8 | 같은 문서 안 `otherLines` 배열 | FR-01-9 ✅, 위치 ✅ 추천대로 |
| 회차 결과 → 알림용 기사 | 1 : 0 또는 1 | `notifyArticleId`에 기사 번호를 적음 (+ 그 기사의 `isNotify: true`) | FR-04-2 ✅, 08 12-1 ① |
| 휴대폰 → 마지막 알림 기사 | 1 : 0 또는 1 | `lastNotifiedArticleId`에 기사 번호를 적음 | FR-04-2 예외 ✅, K7 |

### 2-3. 왜 "회차 문서 1개에 다 넣기"인가 (✅ 추천대로 확정)

| 기준 | ① **회차 문서 1개에 기사·해설·출처·다른 분야를 모두** (채택) | ② 기사마다 문서 1개 (`articles` 컬렉션) | ③ ① + "최신" 표시 문서를 따로 둠 |
|---|---|---|---|
| 앱이 최신 회차를 읽는 횟수 | **1번** (가장 최근 회차 문서 1개) | 기사 수만큼(최대 9번 + 다른 분야) | 1번 (대신 스크립트가 2곳에 써야 함) |
| 알림 시각에 깨어난 짧은 시간 안에 읽기 (08 12-1 ①) | 1번에 끝남 | 여러 번 | 1번 |
| 스크립트 쓰기 | 1번 (한꺼번에) | 기사 수만큼 | 2번, 둘이 어긋날 위험 |
| 문서 크기 한도 (1 MiB) | 회차당 약 80 KB로 충분히 안 ([7-1](#7-1-문서-크기)) | 문제 없음 | 같음 |
| 만들기 쉬움 | 가장 쉬움 | 보통 | 보통 |

- 이유: 앱이 하는 일은 "가장 최근 회차 1개를 통째로 보여주기"뿐이므로(FR-01-7, 지난 뉴스 보기 화면 없음 04 Q16 ✅) 회차 단위로 묶는 것이 가장 단순하고 읽기 횟수도 가장 적습니다.
- 나중에 바꾸기: 구조를 바꾸려면 앱·스크립트의 읽기/쓰기 부분만 고치면 되고, 쌓인 데이터는 새 구조로 다시 만들 필요가 없습니다(과거 회차는 화면에 안 나옴). → 쉽게 고칠 수 있는 기술 세부로 보고 추천대로 확정.

## 3. 표(컬렉션) 정의서 — 데이터 사전

> **표 읽는 법**: "필수"가 ○이면 항상 값이 있음, △이면 비어 있을 수 있음(`null` = 값 없음).
> 자료형: `string`(글자) · `number`(숫자) · `boolean`(참/거짓) · `timestamp`(날짜·시각) · `map`(묶음) · `array`(목록) · `null`(값 없음).
> 필드 이름은 영어 소문자로 시작하는 낙타 표기(camelCase, 예: `hookLine`)로 통일합니다 — 코틀린·파이썬 Firestore 부품의 일반 관례 (✅ 추천대로).
> 예시 값은 **지어낸 예시**입니다.

### 3-1. D1 사용자 설정 — `settings/me` ✅

| 항목 | 내용 |
|---|---|
| 경로 | 컬렉션 `settings`, 문서 ID `me` (고정 — 사용자 1명이라 문서 1개, 03 9장 ✅) |
| 누가 씀 / 읽음 | **앱이 씀**(분야 선택 완료·다시 고르기 완료 때, FR-01-2·01-8) / **스크립트가 읽음**(실행 첫 단계), 앱도 읽음(S04 표시·S01 다시 고르기 미리 선택) |
| 없을 때 | 문서가 없으면 = **분야를 아직 고르지 않음**("나중에 고르기" 포함). 스크립트는 오늘의 화제만 처리 (FR-01-2 예외 ✅) |
| 바꿀 때 | 덮어쓰기(이전 값 이력은 남기지 않음). 각 실행에서 실제로 쓴 분야는 D2 `categoriesUsed`에 남으므로 충분 (✅ 추천대로) |

| 필드 | 자료형 | 필수 | 설명 | 예시 값 | 근거 |
|---|---|:---:|---|---|---|
| `firstCategory` | string (큰 분야 코드) | ○ | 1순위 큰 분야 | `"science"` | FR-01-1 ① ✅ |
| `deepCategory` | string (깊은 분야 코드) | ○ | 1순위 큰 분야 안의 깊은 분야. 반드시 `firstCategory`에 속해야 함 | `"science_space"` | FR-01-1 ② ✅ |
| `secondCategory` | string (큰 분야 코드) | ○ | 2순위 큰 분야. `firstCategory`와 같으면 안 됨 | `"economy"` | FR-01-1 ③ ✅ |
| `updatedAt` | timestamp | ○ | 저장 시각 (서버 시각으로 기록) | `2026-10-26 09:12 KST` | 03 9장 D1 "저장 시각" ✅ |
| `schemaVersion` | number | ○ | 데이터 모양 버전. 지금은 `1`. 나중에 모양을 바꾸면 올림 | `1` | ✅ 추천대로 (신규) |

- 값 검사(✅ 추천대로): 앱은 화면에서 규칙을 지키게 하고(04 S01 입력 검증 ✅), 스크립트도 읽을 때 한 번 더 검사합니다. 규칙이 깨진 값(없는 코드, 깊은 분야가 다른 큰 분야 소속, 1·2순위가 같음)이면 **분야 없음과 똑같이** 처리하고 실행 기록에 경고 `SETTINGS_INVALID`를 남깁니다.

### 3-2. D2 실행 기록 — `runs/{runId}` ✅

| 항목 | 내용 |
|---|---|
| 경로 | 컬렉션 `runs`, 문서 ID = `runId` |
| 문서 ID 규칙 (✅ 추천대로) | **실행을 시작한 한국 시각** `YYYYMMDD-HHmm` (예: `20261026-1137`). 글자 순서 = 시간 순서라 정렬이 쉽고, 콘솔에서 눈으로 찾기 쉬움. 수동 실행도 같은 규칙 |
| 누가 씀 / 읽음 | **스크립트만 씀** / **사람이 Firebase 콘솔(관리 화면)에서 읽음**. 앱 화면(04)에는 실행 기록을 보여주는 곳이 없으므로 **앱은 읽지 않아도 됩니다**(03 9장은 "앱·사람이 읽음" — 앱 읽기 허용 여부는 [09](09_보안_개인정보.md)에서 결정) |
| 쓰는 시점 (✅ 추천대로) | ① 시작할 때 `status: "running"`으로 1번 쓰기 ② 끝날 때 결과로 1번 고쳐 쓰기. → 스크립트가 중간에 멈추면 `running`으로 남아 **어디서 멈췄는지** 알 수 있음 |

| `categoriesUsed` | map | △ | 이번 실행에 쓴 분야 `{first, deep, second}`. 분야 없으면 `null` | `{first:"science", deep:"science_space", second:"economy"}` | FR-01-2 완료 기준 ✅ / 항목 신규 |

### 3-3. 회차 결과 — `editions/{editionId}` ✅

| 항목 | 내용 |
|---|---|
| 경로 | 컬렉션 `editions`, 문서 ID = `editionId` = 같은 실행의 `runId` (예: `20261026-1137`) |
| 누가 씀 / 읽음 | **스크립트만 씀**(실행 마지막에 1번) / **앱이 읽음**(목록·종합 기사 화면, 알림 부품) |
| 언제 저장 | 이번 회차에 **새로 만든 종합 기사가 1개 이상**일 때만. 0개면 저장하지 않음 → 앱은 직전 회차를 그대로 봄 (FR-02-6 예외 ✅) |
| 고치기 | 저장한 뒤에는 고치지 않음 (한 번 쓰고 끝) (✅ 추천대로) |

| 필드 | 자료형 | 필수 | 설명 | 예시 값 | 근거 |
|---|---|:---:|---|---|---|
| `editionId` | string | ○ | 문서 ID와 같은 값 | `"20261026-1137"` | ✅ 추천대로 |
| `slot` | string (회차 코드) | ○ | 아침/점심/저녁. S02 "10월 26일 점심 뉴스" 표시에 사용 | `"noon"` | 03 9장 D3 "회차" ✅, 04 S02 #6 ✅ |
| `createdAt` | timestamp | ○ | 저장 시각. **앱이 최신 회차를 찾는 기준** ([5장](#5-앱이-최신-회차를-찾는-방법)) | `2026-10-26 11:44 KST` | 03 9장 D3 "만든 시각" ✅ |
| `notifyArticleId` | string | △ | 알림용 한 줄이 있는 기사 번호. AI 고르기 실패 시 원문 기사 수가 가장 많은 기사 번호. 둘 다 없으면 `null` | `"20261026-1137_interest_1"` | FR-04-2 ✅, 08 12-1 ① |
| `articles` | array of map | ○ | D3 종합 기사 목록 (1~9개). **페이지 순서(today → interest → recommend), 그 안에서 `order` 순서**로 정렬해 저장 | [3-4](#3-4-d3-종합-기사--articles-배열의-한-칸) | 03 9장 D3 ✅ |
| `otherLines` | array of map | ○ | D7 다른 분야 한 줄 (0~8개). 비어 있으면 앱은 그 칸을 숨김 | [3-7](#3-7-d7-다른-분야-한-줄--otherlines-배열의-한-칸) | FR-01-9 ✅ |
| `schemaVersion` | number | ○ | `1` | `1` | ✅ 추천대로 |

**"직전 회차 결과 유지"를 지키는 방법 (✅ 추천대로)**
- FR-01-4·5·6 예외 ✅: 어떤 페이지가 이번 회차에 실패하면(구글 RSS 오류, 네이버 오류 등) **그 페이지는 직전 회차 결과를 유지**해야 합니다.
- 앱이 여러 회차를 섞어 읽지 않도록(읽기 1번 유지), **스크립트가 직전 회차 문서에서 그 페이지 기사들을 그대로 복사**해 이번 회차 문서에 넣습니다. 복사한 기사는 `carriedFrom`에 원래 회차 ID를 적고, `articleId`는 **원래 번호 그대로** 둡니다.
- 복사한 기사는 **알림용 후보에서 뺍니다** (FR-04-2 ✅ "이번 회차에 만든 한 줄들 중"). 그래서 실행 기록의 `pageResults.*.result`가 `carried`가 됩니다.
- 이를 위해 스크립트는 실행마다 직전 회차 문서를 1번 읽습니다(읽기 1회 추가).

### 3-4. D3 종합 기사 — `articles` 배열의 한 칸 ✅

| 필드 | 자료형 | 필수 | 설명 | 예시 값 | 근거 |
|---|---|:---:|---|---|---|
| `articleId` | string | ○ | **기사 고유 번호** = `{만든 회차 ID}_{페이지 코드}_{순서}`. 알림을 누르면 이 번호로 S03을 엶 | `"20261026-1137_today_2"` | FR-04-3 ✅, 08 12-1 ① / 규칙 ✅ 추천대로 |
| `page` | string (페이지 코드) | ○ | `today` / `interest` / `recommend` ([4-1](#4-1-페이지-page)) | `"today"` | 03 9장 D3 "페이지" ✅ |
| `order` | number | ○ | 페이지 안 순서 1~3 (서버가 정한 순서, 오늘의 화제는 RSS 순서) | `2` | 03 9장 D3 "순서" ✅, FR-01-7 |
| `hookLine` | string | ○ | 어그로 한 줄. **공백 포함 40자 이내**(넘으면 40자 + "…"), 비면 `title`로 대신 | `"내일부터 지하철이 멈춘다고?"` | FR-03-2 ✅ |
| `title` | string | ○ | 종합 기사 제목 1줄 | `"서울 지하철 노조, 내일 파업 예고"` | FR-02-3 ✅ |
| `body` | string | ○ | 종합 기사 본문 600~1,000자 (AI가 새로 쓴 글, 원문 복사 아님). 문단 구분은 줄바꿈 | `"서울교통공사 노동조합이 …"` | FR-02-3 ✅ |
| `conclusion` | string | ○ | 한 줄 결론 | `"출근길에는 버스 등 다른 길을 미리 알아 두는 게 좋겠어요."` | FR-02-3 ✅ |
| `isNotify` | boolean | ○ | 알림용 한 줄이면 `true` (회차 문서의 `notifyArticleId`와 반드시 일치) | `false` | 03 9장 D3 "알림용 여부" ✅ |
| `createdAt` | timestamp | ○ | 이 기사를 만든 시각 (복사한 기사는 원래 시각 유지) | `2026-10-26 11:42 KST` | 03 9장 D3 "만든 시각" ✅ |
| `carriedFrom` | string | △ | 직전 회차에서 복사해 온 기사면 원래 회차 ID, 이번에 만들었으면 `null` | `null` | ✅ 추천대로 (신규) |
| `words` | array of map | ○ | D4 어려운 단어 해설 0~5개 (없으면 빈 목록) | [3-5](#3-5-d4-어려운-단어-해설--words-배열의-한-칸) | FR-02-4 ✅ |
| `sources` | array of map | ○ | D5 출처 1~5개 (0개인 기사는 만들지 않음) | [3-6](#3-6-d5-출처--sources-배열의-한-칸) | FR-02-5 ✅ |

- ✅ 확정: 원문 기사 **본문 전체는 어디에도 저장하지 않습니다** (03 9장). `body`는 AI가 새로 쓴 600~1,000자 정리입니다.
- 사진 항목은 없습니다 (04 1-3 ✅ 사진 없음).

### 3-5. D4 어려운 단어 해설 — `words` 배열의 한 칸 ✅

| 필드 | 자료형 | 필수 | 설명 | 예시 값 | 근거 |
|---|---|:---:|---|---|---|
| `word` | string | ○ | 본문에 **실제로 있는** 단어 (없는 단어는 스크립트가 버림). 앱은 처음 나온 곳에만 밑줄 | `"파업"` | FR-02-4 ✅ |
| `explanation` | string | ○ | 쉬운 해설 1~2문장(100자 안팎) | `"일하는 사람들이 요구를 알리려고 함께 일을 멈추는 거예요."` | FR-02-4 ✅ |

### 3-6. D5 출처 — `sources` 배열의 한 칸 ✅

| 필드 | 자료형 | 필수 | 설명 | 예시 값 | 근거 |
|---|---|:---:|---|---|---|
| `press` | string | ○ | 언론사 이름. 알 수 없으면 원문 주소의 사이트 이름(도메인)으로 대신 (아래 ⚠ 참고) | `"한빛일보"` | FR-02-5 ✅ "언론사 · 기사 제목" |
| `title` | string | ○ | 원문 기사 제목 | `"지하철 노조 내일 총파업"` | 03 9장 D5 ✅ |

### 3-7. D7 다른 분야 한 줄 — `otherLines` 배열의 한 칸 ✅ (신규 위치)

> 03 9장 D1~D5에 저장 위치가 빠져 있던 FR-01-9 결과입니다(08 12-1 ④). **회차마다** 다시 만들므로 회차 문서 안에 둡니다. 번호는 삭제된 D6을 다시 쓰지 않고 **D7**로 붙입니다 (✅ 추천대로).

| 필드 | 자료형 | 필수 | 설명 | 예시 값 | 근거 |
|---|---|:---:|---|---|---|
| `category` | string (큰 분야 코드) | ○ | 사용자가 고르지 않은 큰 분야. 앱은 이 코드로 분야 이름표를 표시 | `"sports"` | FR-01-9 ✅ |
| `hookLine` | string | ○ | 어그로 한 줄 (40자 규칙·금지 규칙 FR-03 그대로) | `"오늘 밤, 야구장이 뒤집혔다"` | FR-01-9 ✅ |
| `articleTitle` | string | ○ | 고른 원문 기사의 제목 (화면에는 안 보임, 콘솔 확인용) | `"프로야구 가을야구 끝내기 승"` | ✅ 추천대로 (신규) |
| `url` | string | ○ | 누르면 브라우저로 여는 **원문 기사 1개** 링크 | `"https://…"` | FR-01-9 ✅ |
| `linkType` | string (링크 종류 코드) | ○ | `original` 또는 `naver` (네이버 검색 결과에 원문 링크가 없을 때) | `"original"` | ✅ 추천대로 |
| `press` | string | △ | 언론사 이름(3-6 ⚠과 같은 조건) | `null` | ✅ 추천대로 |
| `publishedAt` | timestamp | △ | 원문 기사 날짜 | `2026-10-26 09:30 KST` | ✅ 추천대로 |

- 개수·순서: 최대 8개, 기사가 없는 분야는 뺌, AI 호출이 실패하면 **빈 목록**으로 저장 → 앱은 이 칸 전체를 숨김 (FR-01-9 예외 ✅). 저장 순서는 큰 분야 코드표([4-8](#4-8-큰-분야깊은-분야-코드)) 순서 (✅ 추천대로).
- 분야를 고르지 않은 회차에는 만들지 않으므로 빈 목록입니다 (FR-01-9 예외 ✅).
- 본문 추출·종합 기사·단어 해설은 하지 않으므로 그 항목이 없습니다 (FR-01-9 ✅).

## 4. 공통코드·상태값

> 데이터에는 **짧은 영어 코드**를 저장하고, 화면에 보이는 한국어 이름은 앱이 이 표로 바꿔 보여줍니다. 코드는 한 번 정하면 바꾸지 않고, 화면 이름은 자유롭게 바꿔도 됩니다 (✅ 추천대로).

### 4-1. 페이지 (`page`)

| 코드 | 화면 이름 | 근거 |
|---|---|---|
| `today` | 오늘의 화제 | FR-01-4 ✅ |
| `interest` | 나의 관심 분야 | FR-01-5 ✅ |
| `recommend` | 추천 뉴스 | FR-01-6 ✅ |

### 4-2. 회차 (`slot`)

| 코드 | 화면 이름 | 예약 실행 시각 (KST) | 정하는 규칙 (✅ 추천대로) |
|---|---|---|---|
| `morning` | 아침 | 6:30 | 실행 시작이 0:00~9:59 |
| `noon` | 점심 | 11:30 | 10:00~15:59 |
| `evening` | 저녁 | 18:30 | 16:00~23:59 |

- 예약 실행이 몇 분 늦어도, 수동 실행이어도 위 시간대로 정합니다 (FR-01-3 ✅ 6:30·11:30·18:30).

### 4-3. 실행 상태 (`status`)

| 코드 | 뜻 | 회차 결과 저장 |

| `failed` | 저장 단계 등에서 오류로 실행 실패 (GitHub 실패 메일도 감) | × |

> 근거: FR-02-6 ✅(일부 성공 저장, 0개면 저장 안 함, 저장 오류는 실행 실패). 코드 이름은 ✅ 추천대로.

|---|---|---|

## 5. 앱이 최신 회차를 찾는 방법 (읽기 횟수 최소화) ✅ 추천대로

> 근거: FR-01-7 ✅(앱을 열 때마다·당겨서 새로고침 때 최신 회차 읽기), FR-04-2 ✅(알림 시각에 최신 회차의 알림용 한 줄), 08 12-1 ①(한 번의 읽기로)

### 5-1. 읽기 방법

| 상황 | 읽는 것 | 읽기 횟수 (Firestore 계산 기준) |
|---|---|:---:|
| 앱 열기 / 당겨서 새로고침 (S02) | `editions` 컬렉션에서 **`createdAt`이 가장 늦은 문서 1개**만 (정렬 + 1개 제한 조회) | 1 |
| 알림 시각 (K6) | 위와 같은 조회 1번 → 그 문서의 `notifyArticleId`로 한 줄 찾기 | 1 |
| 목록 칸 누름 → S03 | 이미 읽은 회차 문서 안에서 찾음 | 0 |
| 알림 누름 → S03 (앱이 꺼져 있던 경우) | 알림에 담아 둔 `editionId`로 그 문서 1개 읽기 (휴대폰 보관본이 있으면 그것) | 0~1 |
| S04 설정 / S01 다시 고르기 미리 선택 | `settings/me` 1개 | 1 |
| 분야 저장 (S01 완료) | `settings/me` 쓰기 | 쓰기 1 |

- 알림에는 **`editionId`와 `articleId` 두 가지를 담아** 둡니다 (✅ 추천대로). 알림을 누르면 `editionId` 문서에서 `articleId`가 같은 기사를 찾아 S03을 열고, 뒤로 가기 때는 그 기사의 `page` 탭으로 돌아갑니다 (04 Q7 ✅). 못 찾으면 M7 "기사를 불러오지 못했어요" (FR-04-3 예외 ✅).

### 5-2. 알림 부품의 판단 순서 (FR-04-2 ✅ 동작을 데이터로 옮김)

```
 ① 최신 회차 문서 1개 읽기 (인터넷 없으면 휴대폰 보관본 = 직전에 읽은 회차)
 ② 알림 기사 정하기
      notifyArticleId 있음 → 그 기사
      없음 → 오늘의 화제(page=today) order 1 기사
             (오늘의 화제도 없으면 articles 맨 앞 기사 — ✅ 추천대로 보충)
 ③ 그 articleId == 휴대폰의 lastNotifiedArticleId ?
      같음 → 이번 알림 보내지 않음 (같은 알림 반복 방지)
      다름 → 알림 1개 표시 (제목 "뉴스 봐", 내용 = hookLine)
             + lastNotifiedArticleId·lastNotifiedAt 저장
 ④ 다음 시각 1개 다시 예약 (08 ADR-006)
```

- 기사 번호에 회차 ID가 들어 있으므로(`20261026-1137_today_1`), **새 회차가 오면 번호가 반드시 달라져** 알림이 나가고, 서버 실행이 실패해 직전 회차가 그대로면 번호가 같아 **보내지 않습니다**.

### 5-3. 인터넷 없음 판단

- Firestore 앱용 부품은 읽은 결과가 **휴대폰 보관본에서 왔는지** 알려 줍니다. 보관본에서 왔으면 S02에 M3 "인터넷 연결이 없어 이전 뉴스를 보여드려요"를 띄우고, 보관본도 없으면 M4 (FR-01-7 예외 ✅).
- 결과 문서가 하나도 없으면(첫 실행 직후) M5 "다음 뉴스는 ○시에 도착해요" (FR-01-7 ✅).
- 회차 문서는 있는데 어떤 페이지 기사가 0개이고 `settings/me`가 없으면 M6, 있으면 M5 (04 Q12 ✅).

## 6. 휴대폰 안 보관 (K7) ✅ 추천대로

> 근거: 08 K7 ✅(동작), 08 6장(보관 방법은 06에서 정함) → 이 문서에서 정함. 08이 제안한 방법 그대로입니다.

| # | 보관하는 것 | 보관 방법 | 항목 | 쓰는 곳 |
|:---:|---|---|---|---|
| ① | 마지막으로 읽은 결과 (최신 회차 문서, `settings/me`) | **Firestore 앱용 부품의 기본 휴대폰 보관 기능**. 안드로이드에서는 **기본으로 켜져 있고**, 기본 보관 한도는 100 MB입니다(공식 문서 확인, [참고 자료](#참고-자료-2026-10-26-확인)). 따로 만들 것 없음 | (Firestore 문서 그대로) | FR-01-7·02-7 인터넷 없을 때 보여주기, FR-04-2 인터넷 없을 때 직전 회차 |
| ② | 마지막으로 알림 보낸 한 줄 번호 | **SharedPreferences** (앱 안 작은 설정 저장 칸) | `lastNotifiedArticleId` (string, 예 `"20261026-1137_today_1"`, 처음엔 없음) | FR-04-2 예외 중복 알림 막기 |
| ③ | 마지막으로 알림 보낸 시각 | SharedPreferences | `lastNotifiedAt` (숫자, 1970년부터 지난 밀리초) — 실측 확인용(10 테스트) | NFR-03 실측 보조 |

- ①이 충분한 이유: 회차 문서 1개가 약 80 KB이므로 100 MB 한도면 1,000개 넘게 들어갑니다. 한도를 넘으면 오래 안 쓴 것부터 자동으로 지워지는데, 앱이 필요한 것은 **가장 최근에 읽은 회차 1개**뿐이라 문제없습니다.
- ⚠ 확인 못 한 것: 휴대폰 보관본에서 읽은 경우 Firestore 읽기 횟수로 계산되는지는 공식 요금 문서에서 명시 문구를 찾지 못했습니다. 어느 쪽이든 [7-2](#7-2-무료-한도-대비-계산) 계산에서 한도의 0.5%도 안 되므로 영향은 없습니다.
- 휴대폰 안에 **새로 저장하지 않는 것**: 분야 선택(서버 `settings/me`와 그 보관본으로 충분), 알림 권한 상태(안드로이드에 매번 물어봄), 다음 알림 시각(재부팅 때 다시 계산, ADR-006).

## 7. 용량·무료 한도 계산 (누적 보관 기준)

> 근거: 결과를 지우지 않고 쌓아 둠 (FR-02-6 ✅), 비용 0원 (NFR-04 ✅), 08 12-1 ⑥.
> **무료 한도 숫자 출처**: Firebase 공식 문서 "Cloud Firestore 사용량 및 한도(Quotas)" 페이지 — 2026-10-26 확인 ([참고 자료](#참고-자료-2026-10-26-확인)). 한도는 바뀔 수 있으므로 구현 직전에 Firebase 콘솔에서 다시 확인합니다.

### 7-1. 문서 크기

한글 1글자 = 약 3바이트로 계산 (영어·숫자·주소는 1바이트).

| 항목 | 계산 | 크기 (약) |
|---|---|---:|
| 종합 기사 1편 — 본문 | 1,000자 × 3 | 3.0 KB |
| 　제목·어그로 한 줄·결론 | (40 + 40 + 60)자 × 3 | 0.4 KB |
| 　단어 해설 5개 | 5 × (단어 10자 + 해설 100자) × 3 | 1.7 KB |
| 　출처 5개 | 5 × (제목 60자×3 + 주소 약 250 + 언론사·날짜·코드 약 70) | 2.5 KB |
| 　필드 이름 등 덧붙는 몫 | | 0.4 KB |
| **종합 기사 1편 합계** | | **약 8 KB** |
| 회차 문서 — 종합 기사 최대 9편 | 9 × 8 KB | 72 KB |
| 　다른 분야 한 줄 최대 8개 | 8 × (한 줄 40자 + 제목 60자) × 3 + 주소 등 | 4 KB |
| **회차 문서 1개 (최대)** | | **약 80 KB** |
| 실행 기록 문서 1개 | 경고 10개 정도 포함 | 약 2 KB |
| 사용자 설정 문서 | | 0.2 KB 미만 |

- Firestore 문서 1개의 최대 크기는 **1 MiB**(약 1,048 KB)입니다 (공식 문서 확인). 회차 문서 최대 80 KB는 그 **약 8%**라 충분합니다.
- Firestore 저장 용량에는 데이터 말고도 **자동 인덱스·부가 정보가 포함**됩니다(공식 요금 문서 확인). 그 정확한 크기는 확인하지 못했으므로, 아래 계산은 **넉넉히 2배**로 잡습니다. ([8-3](#8-3-인덱스-정책) 인덱스 제외 설정을 하면 실제로는 더 작아집니다.)

### 7-2. 무료 한도 대비 계산

| 항목 | 무료 한도 (공식 문서) | 우리 사용량 (최대로 잡음) | 한도 대비 |
|---|---|---|:---:|
| **저장 용량** | 1 GiB | 하루 3회차 × (80 + 2) KB × 2배 ≈ **하루 0.5 MB** → 2주 약 7 MB, 1년 약 180 MB | 2주 약 0.7%, 1년 약 17% (→ 계속 보관해도 **약 5년** 이상) |
| **문서 읽기** | 하루 50,000번 | 앱 열기·새로고침 하루 30번 × (회차 1 + 설정 1) = 60, 알림 3, 알림 누름 3, 스크립트 3회 × (설정 1 + 직전 회차 1) = 6, 콘솔 확인 수십 번 → **하루 약 150번** | 약 0.3% |
| **문서 쓰기** | 하루 20,000번 | 스크립트 3회 × (실행 기록 2 + 회차 1) = 9, 분야 저장 가끔 → **하루 약 10번** | 0.1% 미만 |
| **문서 삭제** | 하루 20,000번 | 0번 (지우지 않음) | 0% |
| **내려받는 데이터 양** (서버 → 휴대폰·스크립트) | 한 달 10 GiB | 회차 문서 80 KB × 하루 약 40번 ≈ 하루 3.2 MB → **한 달 약 100 MB** | 약 1% |

- 결론: 사용자 1명이라 **어느 한도에도 가깝지 않습니다.** 2주는 물론 몇 년을 쌓아도 무료 범위 안입니다.
- 주의(공식 문서): ① 하루 한도는 **미국 태평양 시간 자정 무렵**(한국 시각 오후 4~5시쯤) 초기화됩니다. ② 무료 데이터베이스는 **프로젝트당 1개**입니다. ③ 결과가 0건인 조회도 **읽기 1번**으로 계산됩니다. ④ 실시간 감시(리스너) 방식으로 읽으면 문서가 바뀔 때마다 읽기가 계산됩니다 — 우리 앱은 "열 때·당길 때 한 번 읽기" 방식이라 해당 없음.
- 확인 못 한 것: 데이터베이스 위치(지역)에 따라 무료 한도가 달라지는지는 공식 문서에서 명시 문구를 찾지 못했습니다 → [10장](#10-사용자-확인이-필요한-항목) Q1에서 만들 때 화면으로 확인.

## 8. 누가 쓰고 누가 읽나 · 관계·인덱스 정책

### 8-1. 쓰기·읽기 주체 (접근 규칙의 근거)

> 접근 규칙(누구에게 무엇을 허락·차단할지) **자체는 [보안·개인정보(09)](09_보안_개인정보.md)** 에서 정합니다. 여기서는 **필요한 만큼만** 적습니다.

| 데이터 | 파이썬 스크립트 (서비스 계정) | 안드로이드 앱 | 사람 (Firebase 콘솔) |
|---|---|---|---|
| `settings/me` (D1) | 읽기 | **쓰기**·읽기 (이 문서 1개만) | 읽기 (FR-01-2 완료 기준) |
| `runs/*` (D2) | **쓰기**(만들기·고치기) | 필요 없음 (화면에 안 나옴) | 읽기 |
| `editions/*` (D3·D4·D5·D7) | **쓰기**(만들기만), 직전 회차 읽기 | 읽기만 | 읽기 |
| 휴대폰 안 (K7) | — | 읽기·쓰기 | — |
| 삭제 | 하지 않음 (✅ Q2: 계속 보관, 자동 삭제 없음) | 하지 않음 | 필요하면 사람이 콘솔에서 |

### 8-2. 관계·무결성 규칙 (✅ 추천대로 — 스크립트가 저장 전에 검사)

Firestore는 관계형 데이터베이스처럼 연결을 자동 검사하지 않으므로, **스크립트가 저장 직전에** 아래를 검사하고 어긋나면 그 항목을 빼거나 고친 뒤 저장합니다.

| # | 규칙 | 어긋나면 |
|:---:|---|---|
| R1 | `editions/{id}`의 `id` = 같은 실행의 `runs/{id}` | (같은 값을 쓰므로 생기지 않음) |
| R2 | `notifyArticleId`는 `articles` 안에 있고, 그 기사는 `carriedFrom: null`, `isNotify: true`. 다른 기사는 모두 `isNotify: false` | 기사 수 기준 대체(FR-04-2), 그래도 없으면 `null` |
| R3 | 페이지마다 기사 0~3개, `order`는 1부터 빈틈없이 | 순서 다시 매김 |
| R4 | 기사마다 `sources` 1~5개 | 0개면 그 기사를 만들지 않음 (FR-02-5 ✅) |
| R5 | `words[].word`는 `body` 안에 있는 글자, 0~5개 | 없는 단어는 버림 (FR-02-4 ✅) |
| R6 | `hookLine` 40자 이하, 비어 있지 않음 | 자르기 + "…", 비면 `title` (FR-03-2 ✅) |
| R7 | `otherLines[].category`는 `settings/me`의 1·2순위가 아닌 큰 분야, 분야마다 최대 1개 | 그 줄을 뺌 (FR-01-9 ✅) |
| R8 | `articleId`는 회차 문서 안에서 중복 없음 | (규칙상 생기지 않음) |
| R9 | `settings/me` — `deepCategory`는 `firstCategory` 소속, `secondCategory ≠ firstCategory` | 분야 없음으로 처리 + `SETTINGS_INVALID` |

### 8-3. 인덱스 정책 (✅ 추천대로)

| 조회 | 누가 | 조건 | 필요한 인덱스 |
|---|---|---|---|
| 최신 회차 1개 | 앱(S02·알림), 스크립트(직전 회차) | `editions`를 `createdAt` 늦은 순으로 1개 | **자동 인덱스**(필드 1개짜리)로 충분 — 따로 만들 것 없음 |
| 특정 회차 1개 | 앱(알림 누름) | 문서 ID로 바로 읽기 | 필요 없음 |
| 사용자 설정 | 앱, 스크립트 | 문서 ID `me`로 바로 읽기 | 필요 없음 |
| 실행 기록 보기 | 사람(콘솔) | 문서 ID 순(= 시간 순) 보기 | 필요 없음 |

- **여러 필드를 묶은 인덱스(복합 인덱스)는 만들지 않습니다.** 위 조회 말고 다른 조건으로 찾을 일이 없습니다.
- **인덱스 제외 설정(추천)**: `editions`의 `articles`·`otherLines` 필드는 그 안의 값으로 찾을 일이 없으므로, Firebase 콘솔에서 이 두 필드를 **자동 인덱스에서 제외**합니다. 긴 본문 글이 인덱스로 한 번 더 저장되는 것을 막아 저장 용량을 줄입니다. 콘솔에서 언제든 켜고 끌 수 있습니다.
- 새 조회가 필요해지면(예: 나중에 "지난 뉴스" 화면) 그때 인덱스를 추가합니다. Firestore는 필요한 인덱스가 없으면 오류 메시지에 만드는 링크를 알려 줍니다.

## 10. 사용자 확인이 필요한 항목

> **되돌리기 어렵거나 사용자 경험에 영향을 주는 것만** 중요한 순서로 적었습니다. 나머지 기술 세부(이름·자료형·코드 등)는 사용자 기준에 따라 "추천대로 확정"했습니다.

| 우선 | 질문 | 추천안 | 왜 되돌리기 어려운가 | 관련 |
|:---:|---|---|---|---|
| ✅ Q1 (사용자 확정 v1.1: 서울) | Firestore 데이터베이스를 만들 때 고르는 **저장 위치(지역)** 를 **서울(`asia-northeast3`)** 로 할까요? | 서울 | 공식 문서: **한 번 만들면 위치를 바꿀 수 없습니다.** 바꾸려면 데이터베이스를 새로 만들어 옮겨야 함. 서울은 지원 지역 목록에 있음(확인). 휴대폰과 가까워 화면 열기가 빠름(NFR-02). ⚠ 위치별 무료 한도 차이는 공식 문서에서 확인 못 함 → 만들 때 화면에 "무료" 안내가 있는지 보고 결정 | NFR-02·04, A5·A6 |
| ✅ Q2 (사용자 확정 v1.1: 계속 보관) | 쌓인 결과(회차 문서·실행 기록)를 **2주 사용 기간이 끝난 뒤에도 계속 보관**할까요, 아니면 **기간(예: 30일)을 두고 자동으로 지울까요?** | **계속 보관 (자동 삭제 없음)** — 1년 쌓아도 무료 용량의 약 17%. 지우는 기능을 만들지 않으므로 가장 쉬움. 과제가 끝나면 필요할 때 콘솔에서 직접 지움 | 한 번 지운 데이터는 되살릴 수 없음. 보관 기간은 개인정보 "보존·파기" 항목(09)과도 연결 | FR-02-6, 03 9장, 09 |

## 12. 다음 문서로 넘기는 사항

### 12-1. [보안·개인정보(09)](09_보안_개인정보.md) 작성자에게

1. **접근 규칙의 근거**는 [8-1](#8-1-쓰기읽기-주체-접근-규칙의-근거) 표입니다. 앱은 `settings/me` **한 문서만 쓰기**, `editions` **읽기만**, `runs`는 접근 불필요. 스크립트는 서비스 계정으로 접근하며 서비스 계정은 접근 규칙의 적용을 받지 않는 것으로 알려져 있으니(09에서 공식 확인) 열쇠 보관이 핵심입니다.
2. **코드 저장소가 공개**(ADR-010)이므로 앱 설정 파일(Firebase 프로젝트 정보)이 공개될 수 있습니다. 그렇다면 **누구나 같은 프로젝트에 접속을 시도할 수 있으므로**, 접근 규칙이 유일한 방어선입니다(예: 익명 로그인 + 규칙, 08 12-2 ①).
3. `settings/me`에 남이 쓰면 스크립트가 엉뚱한 분야를 처리할 수 있습니다 → 쓰기 허용 범위 + 값 검사(R9, `SETTINGS_INVALID`)를 함께 고려.
4. 개인정보: 저장하는 사용자 데이터는 **분야 선택 3개뿐**(이름·연락처·기기 ID 없음). K7의 `lastNotifiedArticleId`는 개인정보가 아닌 기사 번호.
5. **보존·파기**: 보관 기간은 [10장 Q2](#10-사용자-확인이-필요한-항목) 사용자 결정에 따름(추천: 계속 보관, 과제 종료 후 콘솔에서 직접 삭제).
6. 실행 기록 `errorMessage`·`warnings[].detail`에 **키·서비스 계정 정보·주소의 비밀 값**이 들어가지 않도록 하는 규칙.
7. 데이터베이스 저장 위치(10장 Q1) 결정 결과를 기록.

## 참고 자료 (2026-10-26 확인)

- Firestore 무료 한도(저장 1 GiB, 하루 읽기 50,000·쓰기 20,000·삭제 20,000, 한 달 내려받기 10 GiB, 하루 한도는 태평양 시간 자정 무렵 초기화, 무료 데이터베이스 프로젝트당 1개)·문서 최대 1 MiB: [firebase.google.com — Cloud Firestore Usage and limits](https://firebase.google.com/docs/firestore/quotas)
- 저장 용량에 인덱스·부가 정보 포함, 빈 조회도 읽기 1번, 리스너 읽기 계산: [firebase.google.com — Understand Cloud Firestore billing](https://firebase.google.com/docs/firestore/pricing)
- 안드로이드 휴대폰 보관 기본 켜짐·기본 100 MB: [firebase.google.com — Access data offline](https://firebase.google.com/docs/firestore/manage-data/enable-offline)
- 서울(`asia-northeast3`) 지원, 위치는 만든 뒤 변경 불가: [firebase.google.com — Cloud Firestore locations](https://firebase.google.com/docs/firestore/locations)
- 확인하지 못한 것: 휴대폰 보관본 읽기의 요금 계산 여부, 인덱스가 차지하는 정확한 크기, 위치별 무료 한도 차이, 네이버 검색 API의 언론사 이름 항목 유무.
